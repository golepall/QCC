QCC 自动化测试离线工具设计讨论记录
生成日期：2026-06-11

一、背景和核心判断

当前 QCC 项目的自动化测试部分，不应该继续做成一个大而全的网页工具页。更合理的方向是：

1. QCC 主系统负责项目管理、模板管理、测试项管理、结果归档、报告生成、统计分析。
2. 被测机器上的离线工具负责设备信息采集、自动化脚本执行、人工测试辅助填写、日志和证据收集、结果包导出。
3. 两者通过一个标准化结果包连接起来，最终由 QCC 导入结果包并回填测试记录，生成测试报告。

这个方向更符合实际测试场景：被测机器有时候能联网，有时候不能联网；测试现场经常需要用 U 盘拷贝工具；很多测试项既有自动化部分，也有人工确认部分。


二、推荐方案：离线测试工作台 / 便携式测试 Agent

建议做一个单独的离线测试工具，可以放进 U 盘，也可以复制到被测机器桌面运行。

它的定位不是替代 QCC，而是作为 QCC 的现场测试执行端。

推荐工作流程：

1. 在 QCC 中选择项目，导出一个测试包。
   测试包中包含：
   - 项目编号
   - 产品型号
   - 测试模板
   - 测试项清单
   - 测试步骤和判定标准
   - 预期配置
   - 离线工具程序
   - 脚本映射配置

2. 将测试包拷贝到 U 盘。

3. 在被测机器上运行离线工具。
   最好是免安装 exe，可以直接从 U 盘运行，也可以复制到桌面运行。

4. 工具启动后先采集系统环境。
   需要采集的信息包括：
   - BIOS 厂商、版本、日期
   - 主板型号
   - CPU 型号、核心数、频率
   - 内存条信息、容量、频率、插槽
   - SSD / HDD 型号、容量、接口、类型
   - 显卡型号、驱动版本
   - 有线网卡、无线网卡、蓝牙
   - 声卡、摄像头、触摸板、指纹等外设
   - 操作系统版本、Build、语言
   - 设备管理器异常项
   - 关键驱动版本

5. 工具显示完整测试计划。
   推荐界面结构：
   - 左侧：测试分类和测试项列表
   - 中间：测试步骤、条件、判定标准
   - 右侧：执行按钮、结果填写、备注、日志、截图/证据

6. 自动化和人工测试结合。
   能自动跑的测试项由工具执行并给出建议结果；不能自动跑的测试项由测试员手动填写 Pass / Fail / NA / Blocked。

7. 测试完成后导出结果包。
   不建议只导出单个 JSON，建议导出 zip 包。

8. 将结果包导入 QCC。
   QCC 根据稳定测试项 ID 自动匹配测试记录，完成结果回填，并进入报告中心生成最终报告。


三、离线工具应该支持的测试类型

测试项不应该全部硬写死，而应该做成可扩展的测试脚本体系。

推荐分为五类：

1. 自动采集类
   用于采集硬件、系统、驱动、设备状态等信息。

   示例：
   - BIOS 信息采集
   - CPU 信息采集
   - 内存信息采集
   - 硬盘信息采集
   - 显卡和驱动采集
   - 网卡、声卡、蓝牙、摄像头采集
   - 设备管理器异常检查

2. 自动判定类
   可以根据采集结果和预期配置直接判断 Pass / Fail。

   示例：
   - BIOS 版本是否符合预期
   - CPU 型号是否匹配
   - 内存容量是否满足要求
   - SSD 型号和容量是否匹配
   - 设备管理器是否存在异常设备
   - 驱动版本是否缺失或异常

3. 半自动执行类
   工具可以启动测试、记录过程、保存日志，但最终允许测试员确认。

   示例：
   - Stress 测试
   - S3 睡眠循环
   - S4 休眠循环
   - 重启循环
   - 内存压力测试
   - 磁盘读写压力测试
   - BurnInTest 测试

4. 外部工具封装类
   不必所有工具都自己写，可以调用成熟工具并解析输出。

   示例：
   - CrystalDiskMark
   - FIO
   - iperf3
   - BurnInTest
   - 3DMark
   - SPEC CPU
   - UnixBench
   - STREAM

5. 人工辅助类
   这类测试无法完全自动化，工具提供步骤、标准、截图、备注、结果填写即可。

   示例：
   - 外观检查
   - 接口插拔测试
   - 键盘鼠标测试
   - 显示屏检查
   - 摄像头主观确认
   - 音频播放和录音确认


四、脚本体系设计建议

关键不是每个测试项都写一个孤立脚本，而是建立统一的脚本执行规范。

建议规则：

1. 每个自动化脚本都有唯一 script_id。
2. QCC 测试项通过 test_case 或脚本映射表绑定到 script_id。
3. 离线工具根据测试包中的测试项，找到对应脚本并执行。
4. 所有脚本不管用 Python、PowerShell、BAT、外部 exe，最终都必须返回统一结果格式。
5. 新增测试项时，尽量只新增脚本和映射，不修改离线工具主体。

推荐脚本返回格式：

{
  "test_id": "bios_version_check",
  "script_id": "bios_version_check",
  "verdict": "Pass",
  "message": "BIOS 版本匹配",
  "metrics": {
    "expected": "S2ETMR.01",
    "actual": "S2ETMR.01"
  },
  "raw_output": "",
  "logs": [],
  "duration_ms": 1200
}

推荐测试结果状态：

- NotTested：未测试
- Running：执行中
- Pass：通过
- Fail：失败
- NA：不适用
- Blocked：阻塞
- Manual：需要人工确认
- Error：脚本异常


五、S3 / S4 / 重启类测试的特别要求

S3、S4、重启循环等测试和普通脚本不同，因为机器会睡眠、休眠或重启。

这类测试必须支持：

1. 恢复继续
   工具要知道上一次执行到第几轮，机器恢复后继续记录。

2. 本地状态文件
   每轮开始、结束、结果、时间都写入本地状态文件，避免断电或重启丢失。

3. 开机自启动能力
   如果测试需要重启后自动继续，工具可以注册临时启动任务，测试完成后自动清理。

4. 失败证据
   如果某轮失败，需要记录失败时间、错误信息、日志、必要截图。

5. 人工确认
   即使工具判断通过，也允许测试员最终确认 Pass / Fail。


六、结果包设计

测试完成后，建议导出 zip 格式结果包，而不是只导出一个 JSON。

推荐结构：

QCC_Result_RPT-20260611-001_20260611_153000.zip
  manifest.json
  result.json
  system_info.json
  logs/
  screenshots/
  artifacts/

manifest.json 建议包含：

- 项目编号
- 产品型号
- 测试模板编号
- 工具版本
- 被测机器主机名
- 操作系统信息
- 测试人员
- 开始时间
- 结束时间
- 导出时间
- 结果文件校验信息

result.json 建议包含：

- test_id
- item_no
- test_name
- category
- verdict
- comment
- evidence
- raw_output
- parsed metrics
- duration_ms
- executed_at

system_info.json 保存完整设备采集信息。

logs/ 保存脚本日志、压力测试日志、循环测试日志。

screenshots/ 保存测试证据截图。

artifacts/ 保存外部工具输出文件，例如 CSV、TXT、HTML 报告等。


七、和 QCC 主系统的结合方式

QCC 主系统需要支持两个方向：

1. 导出测试包
   从项目中导出离线工具可识别的 config.json 或完整 zip 包。

2. 导入结果包
   将离线工具导出的结果包导入 QCC，自动完成：
   - 设备配置回填
   - 测试记录回填
   - 日志和证据归档
   - 执行批次记录
   - 未匹配测试项提示
   - 报告中心状态更新

导入时最重要的是测试项匹配。

不建议只靠中文测试项名称匹配，因为模板文字可能变化。应该使用稳定 ID，例如：

- template_code
- category_code
- item_no
- test_case
- script_id

推荐最终匹配优先级：

1. test_case / test_id 精确匹配
2. template_code + category_code + item_no 匹配
3. 测试项名称兜底匹配
4. 未匹配项进入人工确认列表


八、界面设计建议

离线工具界面不需要做成复杂平台，更适合做成现场测试工作台。

推荐主要页面：

1. 项目首页
   显示项目编号、产品型号、测试模板、测试人员、机器信息、整体进度。

2. 系统信息页
   展示自动采集到的 BIOS、主板、CPU、内存、硬盘、显卡、驱动、OS、异常设备。

3. 测试执行页
   左侧分类，右侧测试项详情。

4. 压力/循环测试页
   展示 S3、S4、重启、Stress 等长时间任务的轮次、进度、日志和失败记录。

5. 结果汇总页
   展示 Pass、Fail、NA、Manual、Blocked 统计，列出未完成项和 Fail 项。

6. 导出页
   导出结果包，并提示哪些内容缺失。


九、权限和安全建议

离线工具需要提前考虑权限问题。

1. 启动时检测是否管理员权限。
2. 需要管理员权限的测试项明确提示。
3. 尽量只做读取和测试动作，不随意修改系统配置。
4. S3 / S4 / 重启等会改变机器状态的操作，需要明显确认。
5. 外部工具路径和执行命令需要白名单控制。
6. 结果包中避免保存敏感信息，例如密码、私钥、个人账号信息。


十、实施建议

建议分阶段做，不要一次性追求所有功能。

第一阶段：可用的离线测试闭环

- QCC 导出测试包
- 离线工具读取测试包
- 自动采集系统信息
- 显示测试项列表
- 支持人工填写 Pass / Fail / NA / 备注
- 导出结果包
- QCC 导入结果包并回填测试记录

第二阶段：自动化脚本库

- BIOS 检查
- CPU 检查
- 内存检查
- 硬盘检查
- 显卡检查
- 设备管理器异常检查
- 网络连通性检查
- 驱动版本检查

第三阶段：压力和循环测试

- S3 循环
- S4 循环
- 重启循环
- 内存压力
- 磁盘压力
- BurnInTest 封装

第四阶段：证据和报告增强

- 截图
- 日志归档
- 外部工具输出归档
- Fail 强制备注
- 导入预检查
- 未匹配测试项人工确认


十一、最终结论

这个方向值得做。

它比单纯在网页中做自动化测试更符合现场测试实际，也能解决被测机器不稳定联网的问题。

关键设计原则是：

1. QCC 是管理和报告中心。
2. 离线工具是现场执行中心。
3. 自动化脚本是可持续扩展的工具库。
4. 结果包是两者之间的标准接口。
5. 自动化不能覆盖的地方，要用人工辅助流程兜底。

如果按这个方向建设，后续每增加一个测试项目，不需要重做平台，只需要新增脚本、映射测试项、完善导入规则即可。
