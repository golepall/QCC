# QCC 真实开机自动续跑现场验收步骤

生成日期：2026-06-12

## 1. 目的

本文用于对第一阶段延期项“真实开机自动续跑”执行现场验收，确认当前代码已经从“恢复脚本占位”升级为“可真实触发自动恢复”的最小可用闭环。

本文验收的目标是：

- 标记等待恢复后，Agent 能生成续跑文件并注册当前用户开机启动
- 机器恢复并登录后，Agent 能被自动拉起
- Agent 能识别 `--resume-long-task <task_key>` 并自动恢复到对应长任务
- 恢复成功后，状态能从 `waiting_resume` 切换为 `resumed`
- 任务完成或人工清理后，Startup 启动项会被正确移除

本文不把当前能力定义为“完全无人值守 runtime 恢复执行”。对于 `S3/S4/reboot` 类恢复型任务，当前验收目标是“自动触发恢复链路”，不是“恢复后继续后台 runtime 实例”。

## 2. 适用范围

当前适用的长任务包括：

- `s3_cycle`
- `s4_cycle`
- `reboot_cycle`

不适用于以下真实 runtime 型任务：

- `memory_stress`
- `burnin`

原因：

- 这两类任务走 `StressManager` 的 runtime 执行链路
- 当前“开机自动续跑”实现主要针对恢复型长任务的状态恢复，不是 runtime 进程续跑

## 3. 验收前准备

验收机器需满足以下前置条件：

1. 操作系统为 Windows
2. 能正常登录到将要执行测试的当前用户
3. 已准备可用的 Agent exe 目录和测试包目录，并能正常启动 `QCC_Test_Agent.exe`
4. 当前用户有可写 `%APPDATA%` 目录
5. 长任务页面可正常创建 `S3/S4/重启循环` 计划

建议验收前确认以下路径：

- Agent exe 目录：`d:\QCC\test_engine\dist\QCC_Test_Agent`
- Agent 启动文件：`d:\QCC\test_engine\dist\QCC_Test_Agent\QCC_Test_Agent.exe`
- 文档目录：`d:\QCC\docs`
- Startup 目录：`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup`

建议真实机器按如下目录放置：

- `D:\QCC_TEST\QCC_Test_Agent`
- `D:\QCC_TEST\tmp_stage2_resultmeta_check`

建议启动命令：

- `D:\QCC_TEST\QCC_Test_Agent\QCC_Test_Agent.exe D:\QCC_TEST\tmp_stage2_resultmeta_check\config.json`

## 4. 验收步骤

### 4.1 创建可恢复长任务

1. 启动 `QCC_Test_Agent.exe` 图形界面。
2. 进入“压力/循环测试”页。
3. 创建一个 `S3 睡眠循环`、`S4 休眠循环` 或 `重启循环` 计划。
4. 确认状态文件已生成在测试包目录下的 `agent_runtime` 中。

期望结果：

- 已出现 `agent_runtime\long_task_state.json`
- 当前任务记录中可看到对应 `task_key`

### 4.2 标记等待恢复

1. 在长任务详情中点击“标记等待恢复”。
2. 记录当前任务名称和 `task_key`。
3. 检查 `agent_runtime` 目录中的续跑相关文件。

期望结果：

- 生成 `<task_key>_resume_note.txt`
- 生成 `<task_key>_resume_launcher.cmd`
- 生成 `<task_key>_resume_launcher.ps1`
- `long_task_state.json` 中对应任务的 `resume_state` 为 `waiting_resume`
- `startup_registered` 为 `true`
- `startup_launcher_cmd` 已写入实际 Startup 路径

### 4.3 检查 Startup 注册

1. 打开 Startup 目录：
   `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup`
2. 检查是否出现命名类似 `QCC_AutoResume_<project_code>_<task_key>.cmd` 的文件。
3. 打开该文件，确认其内容会 `call` 到 `agent_runtime` 下的恢复启动脚本。

期望结果：

- Startup 目录中存在对应 `.cmd`
- 脚本内容指向当前测试包的恢复启动脚本

### 4.4 检查恢复启动脚本内容

1. 打开 `agent_runtime\<task_key>_resume_launcher.cmd`
2. 确认其中包含：
   - `QCC_AGENT`
   - `QCC_CONFIG`
   - `QCC_TASK_KEY`
3. 确认启动命令中带有：
   `--resume-long-task "<task_key>"`

期望结果：

- 启动脚本不是占位提示文本
- 启动脚本会真实拉起 `QCC_Test_Agent.exe`
- 参数中明确带出 `--resume-long-task`

### 4.5 执行恢复动作

1. 按测试要求执行一次 `S3/S4/重启` 恢复流程。
2. 机器恢复后，使用同一测试用户登录。
3. 观察 Agent 是否自动拉起。
4. 观察是否自动定位到对应长任务。

期望结果：

- Agent 会在登录后被自动拉起
- Agent 不需要手工点击“恢复继续”
- 状态栏或弹窗提示已自动恢复长任务

### 4.6 恢复后检查状态

1. 恢复进入 Agent 后，查看长任务详情。
2. 打开 `agent_runtime\long_task_state.json`。
3. 检查当前任务记录。

期望结果：

- `resume_state` 从 `waiting_resume` 变为 `resumed`
- `status` 为 `running`
- `resume_count` 至少加 `1`
- `last_resume_at` 已写入时间
- 日志中新增“已在恢复后继续任务，来源 startup”
- `startup_registered` 变为 `false`
- 原 Startup 启动脚本已被移除

### 4.7 完成态清理验证

1. 在恢复后的任务上继续记录轮次，直到达到计划总轮次。
2. 再次查看长任务详情和状态文件。
3. 检查 Startup 目录。

期望结果：

- 任务状态变为 `completed`
- `resume_state` 被清空
- `next_action` 为 `manual_review`
- Startup 目录中不再存在该任务的启动脚本

### 4.8 手工清理验证

1. 再创建一个可恢复长任务并标记等待恢复。
2. 不执行恢复，直接点击“清理续跑文件”。
3. 检查 `agent_runtime` 和 Startup 目录。

期望结果：

- `resume_note_path`、`resume_launcher_cmd`、`resume_launcher_ps1`、`startup_launcher_cmd` 被清空
- `startup_registered` 为 `false`
- 续跑说明、启动脚本、Startup 启动脚本都被删除
- 日志中出现“已清理续跑文件和开机启动注册”

## 5. 验收通过标准

满足以下条件即可判定当前“真实开机自动续跑”最小可用方案通过：

1. 等待恢复后会生成真实启动脚本，而不是提示占位文件
2. Startup 目录能自动注册当前任务的启动项
3. 恢复并登录后，Agent 能自动拉起并触发恢复
4. 恢复成功后，任务状态能从 `waiting_resume` 切到 `resumed`
5. 恢复成功后，Startup 启动项会被自动移除
6. 完成态和手工清理都不会留下脏的 Startup 注册

## 6. 常见失败点

如果现场验收失败，优先检查以下几点：

1. 当前用户是否真的登录到了注册 Startup 的同一用户
2. `%APPDATA%` 是否可写，Startup 目录是否存在
3. `resume_launcher.cmd` 中的 `QCC_AGENT`、`QCC_CONFIG` 路径是否仍然有效
4. 测试包目录是否在恢复后被移动、删除或改名
5. Windows 安全策略是否拦截了登录后启动脚本
6. 当前任务在恢复前是否确实处于 `waiting_resume`

## 8. 当前结论边界

本轮功能可定义为：

- 已完成“真实开机自动触发恢复链路”
- 已支持“自动拉起 Agent + 自动定位任务 + 自动执行恢复动作”

本轮仍不应定义为：

- 完整无人值守长任务执行平台
- 恢复后继续原 runtime 进程实例
- 覆盖所有异常环境的全自动自愈机制
