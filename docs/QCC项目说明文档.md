## 一、项目基础概况

### 1.1 项目立项背景

在硬件产品测试领域，测试报告是质量保障的核心交付物。传统模式下，测试团队面临以下痛点：

| 痛点 | 具体表现 | 影响 |
|------|----------|------|
| **效率低下** | 每份测试报告需手工编写 4-6 小时，涉及 16 个页面、81 个数据点 | 大量人力浪费在重复性排版工作 |
| **格式混乱** | 不同测试员使用不同 Excel 模板版本，审核返工率高达 30% | 报告质量参差不齐，影响客户信任 |
| **数据孤岛** | 测试记录、Bug 数据、设备配置散落在 Excel/邮件/IM 中 | 无法追溯历史数据，无法做趋势分析 |
| **重复劳动** | 相似产品的测试报告需从零编写，历史数据无法复用 | 团队协作效率低，知识无法沉淀 |

为解决上述问题，立项建设 **QCC（Quality Control Circle）测试报告自动化平台**，目标是实现测试报告从手工编写到全流程自动化的转变。

### 1.2 核心目标

1. **效率提升**：将测试报告生成时间从 4-6 小时缩短至 15 分钟以内
2. **质量统一**：建立统一的设计令牌系统，确保所有报告格式 100% 一致
3. **数据贯通**：打通测试记录、Bug 追踪、设备配置、需求管理全链路
4. **知识沉淀**：建立可复用的模板库和历史数据资产

## 二、项目技术架构

### 2.1 技术栈总览

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| **Web 框架** | FastAPI 0.115+ | 异步高性能 Python Web 框架 |
| **模板引擎** | Jinja2 | 服务端渲染 HTML，支持宏/继承/包含 |
| **前端交互** | HTMX 1.9 + Alpine.js 3.13 + 纯 JavaScript | 无框架轻量级 AJAX 交互方案 |
| **CSS 设计系统** | 自定义 Design Token（8 大体系） | CSS 自定义属性驱动的统一设计 |
| **数据库** | SQLite + aiosqlite | 轻量级异步数据库，零运维成本 |
| **ORM** | SQLAlchemy 2.0（async） | 异步 ORM，支持复杂查询 |
| **数据库迁移** | Alembic | 版本化数据库 schema 管理 |
| **认证** | JWT（python-jose）+ Cookie | 双模式认证：页面 Cookie / API Bearer Token |
| **密码安全** | passlib + bcrypt + salt | 加盐哈希存储 |
| **Excel 处理** | openpyxl + xlrd | xlsx 读写 + 旧版 xls 兼容 |
| **日志** | structlog | 结构化日志（已引入，待全面启用） |
| **测试** | pytest + pytest-asyncio + httpx | 异步 API 测试 |
| **代码规范** | ruff | Python 代码格式化和检查 |

### 2.3 核心模块功能与交互逻辑

#### 2.3.1 认证模块 (Auth)

- **Cookie 认证**：页面路由通过 `qcc_token` Cookie 验证用户身份，未登录自动重定向到 `/page/login`
- **Bearer Token 认证**：API 路由通过 `Authorization: Bearer <token>` 头验证，支持第三方集成
- **密码安全**：bcrypt 加盐哈希，每个用户独立 salt
- **JWT 配置**：HS256 算法，72 小时过期

#### 2.3.2 项目管理模块 (Project)

- 项目 CRUD，自动生成项目编号（PRJ-xxxx）
- 关联模板、设备配置、产品
- 项目状态管理：draft → testing → completed
- 支持项目嵌套（parent_id）

#### 2.3.3 模板管理模块 (Template)

- 三级结构：报告模板 → 测试分类 → 测试项
- 模板包含 Sheet 配置、测试项定义、判定标准
- 支持按类别和产品类型筛选

#### 2.3.4 测试记录模块 (Record)

- 按分类分组显示测试项
- 单条记录实时更新（HTMX PUT 请求，局部刷新行）
- 批量设置结果（按分类批量填充未测试项）
- 结果类型：Pass / Fail / NA / Blocked / Error / NotTested

#### 2.3.5 Bug 管理模块 (Bug)

- Bug 自动编号：`{项目编码}-BUG-{序号}`（如 PRJ-0001-BUG-001）
- Bug 创建、编辑、关闭，关联项目
- 严重程度分级：high / medium / low
- 状态流转：open → in_progress → resolved → closed
- 字段结构对齐 Excel Buglist 模板（18 列）：Bug ID、标题、描述、复现步骤、严重程度、状态、MB 信息、BIOS 信息、系统信息、负责人(Owner)、备注等
- 支持从异常问题上报模块自动同步创建

#### 2.3.6 需求管理模块 (Requirement)

- 三类需求：业务需求(BR-)、用户需求(UR-)、开发需求(DR-)
- 需求全生命周期：draft → active → developing → testing → completed → closed
- 字段级变更追踪（requirement_change 表）
- 自动生成需求编号

#### 2.3.7 任务看板模块 (Task)

- 看板视图四列拖拽：todo → doing → done → closed
- 自动生成任务编号（T-xxxx）
- 状态变更自动记录时间戳（started_at / completed_at）
- 关联需求，支持子任务
- 纯 JavaScript 实现（解决 Alpine.js x-data 嵌套作用域冲突）
- 新增字段：类别(category)、项目类别(project_category)、测试工程师(test_engineer)、委托人(client)、委托时间(commission_time)、委托截止(commission_deadline)、开发目标时间(dev_target_time)、样品时间(sample_time)、实际完成时间(actual_complete_time)、进度(progress)、备注(remark)
- 任务详情弹窗支持查看/编辑双模式切换
- 统计数字实时更新（创建/删除/状态变更后自动刷新）

#### 2.3.8 报告中心模块 (Report Center)

- **HTML 报告自动生成**：汇总项目信息、测试记录、Bug 数据，生成完整 HTML 测试报告
- 报告内容包含：封面、测试概况、测试明细（按分类）、缺陷列表、测试结论
- **报告预览**：在线预览生成的 HTML 报告
- **报告下载**：支持下载为 HTML 文件
- **历史报告管理**：查看历史报告列表，支持删除
- 数据导入：设备配置 JSON、测试结果 JSON、日志文件上传
- 导出前完整性检查（Fail 无备注、未测试项检测）

#### 2.3.9 自动化测试模块 (AutoTest)

- 离线测试流程：导出测试包 → 现场执行 → 导入结果归档
- 在线采集：系统信息自动采集
- 远程执行：SSH 连接被测设备执行测试脚本

#### 2.3.10 仪表盘模块 (Dashboard)

- 全局统计：项目数、Bug 数、任务数、模板数
- 最近活动：操作日志实时展示
- 最近项目：快速访问
- 个人工作台：我的任务、我的需求、通知

#### 2.3.11 Excel 模板管理模块 (Excel Template)

- 扫描 `docs/reference/测试报告文件/` 目录下的 xlsx 文件
- 双 Tab 视图：Excel 模板列表 + 数据库模板列表
- Excel 在线预览：多 Sheet 切换，表格形式展示内容
- 模板数据写入：支持向模板填充数据
- 文件权限检查

#### 2.3.12 异常问题上报模块

- 嵌入在测试记录填写页面，与测试流程无缝衔接
- 异常问题提交：标题、描述、严重程度、截图附件
- 问题列表展示：查看已提交的异常问题及处理状态
- 提交时自动同步至 Bug 管理系统，避免重复录入

### 4.2 核心功能演示说明

**典型使用流程**：

1. **创建项目**：选择报告模板 → 填写产品信息 → 自动生成项目编号 → 系统自动创建测试记录
2. **填写记录**：左侧分类导航 → 右侧逐项填写结果/备注 → 单条实时保存 → 批量设置未测试项
3. **异常上报**：发现异常时直接在记录页提交异常问题 → 自动同步至 Bug 管理
4. **查看进度**：项目详情页展示测试进度条、分类统计表、Bug 列表
5. **导入数据**：上传设备配置 JSON / 测试结果 JSON / 日志文件
6. **生成报告**：一键生成 HTML 测试报告 → 在线预览 → 下载/打印

### D. 技术决策说明

| 决策 | 选择 | 原因 |
|------|------|------|
| 为什么选 FastAPI 而非 Flask | FastAPI | 原生异步支持、自动 API 文档、类型提示驱动 |
| 为什么选 HTMX 而非 Vue/React | HTMX | 零构建工具、服务端渲染、学习成本低、适合内部系统 |
| 为什么选 SQLite 者非 MySQL | SQLite | 零运维、单文件部署、当前规模性能足够 |
| 为什么用 Jinja2 模板而非 SPA | Jinja2 | 服务端渲染首屏快、SEO 友好、与 HTMX 天然配合 |
